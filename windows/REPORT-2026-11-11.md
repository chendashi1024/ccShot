# ccShot Windows · 阶段一报告（2026-11-11）

目标见 [GOALS-WINDOWS.md](../GOALS-WINDOWS.md)。本报告只写**实际做过并留下证据**的事，没做的明确写没做。

## 1. 一句话结论

本地 PaddleOCR（PP-OCRv4）+ ONNX Runtime 的路线可行：在同一批原图上，轻量组合的字符错误率 1.47%、
整图一致 15/32，接近或略好于 macOS 原型的 Apple Vision（2.05%、16/32），速度在 CPU 上可接受；
逐字框命中 99.3%、单字拖选 99.2%、整行拖选 100%，说明“截完直接拖选字”在识别层面站得住。
**但所有运行都在 macOS（Apple M4）上完成，Windows 真机上的热键、屏幕捕获、DPI 和安装流程一次都没跑过。**

## 2. 证据边界（先看这段，再看数字）

| 项目 | 实际情况 |
|---|---|
| 测试设备 | Apple M4（10 逻辑核）、macOS 15.4.1（Darwin 24.4.0）、.NET 8.0.428、arm64 |
| 是否 Windows | **不是**。本次没有任何 Windows 设备或虚拟机可用；UTM 已安装但未配置 Windows，也没有远程 Windows 主机 |
| 因此可直接引用的 | OCR 质量、逐字坐标、拖选逻辑、包体、模型加载与推理耗时（同一 CPU 内的相对比较） |
| 因此不能引用的 | Windows 上的绝对速度、热键与捕获是否可用、多屏 DPI 行为、安装/升级/卸载、SmartScreen 提示 |
| 构建证据 | `dotnet build` 与 `dotnet publish -r win-x64` 在 macOS 上 0 错误（`EnableWindowsTargeting`），产物为 Windows PE（CcShot.exe） |

结论措辞按此区分：**“已实现”指代码存在且编译通过；“已实测”只指上面 macOS 那部分。**

## 3. 同图对比结果

样本：两组。

- **A 组（新增，10 张）**：纯英文（1x/2x）、代码（1x 深色/2x）、中文 10pt/11pt 小字、中英混排、低对比、标点密集、紧行距。
  每张都有**逐字真值框**，用于逐字选取评分。生成脚本 `tools/gen_windows_fixtures.py`，图与 manifest 在 `testdata/windows-01/`。
- **B 组（复用 macOS 原型，32 张）**：`prototype/local-ocr/results/2026-11-03-native-01/fixtures/`，
  只用于文字质量对比（无逐字真值，故不参与逐字选取评分）。

### 3.1 汇总

| 样本组 | 组合 | 字符错误率（去空白） | 字符错误率（保留空白） | 整图一致 | 检测 P50 | 识别 P50 | 端到端 P50 / P95 | 模型体积 |
|---|---|---|---|---|---|---|---|---|
| A（10 张） | 轻量 mobile | **0.70%** | 6.79% | **8/10** | 8 ms | 82 ms | **85 / 151 ms** | 14.9 MB |
| A（10 张） | 精度优先 server | 1.76% | 6.17% | 7/10 | 162 ms | 446 ms | 569 / 1091 ms | 194.5 MB |
| B（32 张） | 轻量 mobile | 1.47% | 3.30% | 15/32 | 31 ms | 120 ms | 150 / 167 ms | 14.9 MB |
| B（32 张） | 精度优先 server | **1.02%** | 2.88% | **21/32** | 681 ms | 669 ms | 1347 / 1481 ms | 194.5 MB |

参考（同一批 B 组图，macOS 原型 Apple Vision，来自 `prototype/local-ocr/TEST-REPORT.md`）：
字符错误率 2.05%、整图一致 16/32、识别调用中位 76.55 ms / P95 94.41 ms。
**注意口径**：Apple 那个 76 ms 只是识别调用；Paddle 的 150 ms 是“检测 + 识别”整套。两者不能直接比快慢，
只能说“同一台机器上，Paddle 走完检测+识别仍在一两百毫秒量级”。

### 3.2 按类别看失败（B 组，轻量组合）

| 类别 | 未达整图一致 | 说明 |
|---|---|---|
| 日常中文、产品说明、中文排版 | 0/4、0/4、0/4 | 干净的中文正文全对 |
| 中英混排 | 3/4 | 主要是空格与个别英文单词 |
| 数字标点 | 4/4 | 数字与标点混排差异（全角/半角、空格） |
| 繁体中文 | 4/4 | 字典是简体优先，繁体存在错字 |
| 代码与路径 | 2/4 | 半角括号被识别成全角 `（）`，是主要问题 |
| 近形字 | 4/4 | 近形字专项本来就是要暴露错误 |

精度优先组合在 B 组把“中英混排”和“代码与路径”从 3/4、2/4 错误降到 0 错，代价是 6–10 倍耗时和 13 倍体积。

### 3.3 逐字坐标与拖选（A 组，带逐字真值）

| 组合 | 逐字框命中 | 框边界平均误差 | 归一化误差 | 单字拖选正确 | 整行拖选正确 |
|---|---|---|---|---|---|
| mobile | 565/569 = **99.3%** | 1.25 px | 0.108 个字符宽 | 510/514 = **99.2%** | 23/23 = **100%** |
| server | 564/569 = 99.1% | 1.14 px | 0.100 个字符宽 | 500/514 = 97.3% | 23/23 = 100% |

读法：逐字框不是“把行框均分”，而是识别器 CTC 时间步 + 相邻字符中点划分出来的独立区间；
命中率按“预测框中心落在真值框内”统计；单字拖选是在真值字框内 30%–70% 处拖，看剪贴板是否得到恰好一个字符。
**这些是逻辑与识别层面的证据，不是 Windows 界面上的鼠标操作证据。**

### 3.4 空格恢复（工程取舍）

识别器经常丢掉英文单词间的空格（“Thequickbrownfox”）。字符框是首尾相接的，没有间隙信息可用，
所以改用**像素空白列**：在相邻两个拉丁字符之间找空白带，宽度超过行高 25% 就插一个空格字符（中文永不插入）。
A 组保留空白的字符错误率从 8.64% 降到 6.79%，B 组从 3.51% 降到 3.30%；忽略空格的字符错误率不变。

自包含包偏大，主要是 .NET 桌面运行时；如果试用者愿意装运行时，框架依赖包只有 18.3 MB。

## 4. 候选组合取舍（建议）

**默认发轻量组合（14.9 MB，端到端 85–150 ms），精度优先组合作为可选“高精度模型包”单独下载。**

理由：
- 截图选字是“截完马上要结果”的场景，569–1347 ms 的等待会明显破坏体验；
- 轻量组合在中文正文上已经全对，主要差距集中在繁体、近形字和代码括号，这些不是日常截图的主体；
- 长文本（B 组 3 行 × 数十字的图）上精度优先组合确实更好（1.02% vs 1.47%，整图一致 21/32 vs 15/32），
  值得作为“需要时再下”的可选项，而不是默认负担。
